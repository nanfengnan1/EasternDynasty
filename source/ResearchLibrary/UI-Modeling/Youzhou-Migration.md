# 幽州方格地图：本地代码迁移审查

审查日期：2026-10-25。依据：[重做基线](../../Docs/Research/2026-10-25-Visual-Reset.md) 与当前项目源码。本轮仅检查和写本文，没有修改 Assets、Builds、存档或正在运行的客户端，没有启动 Unity。

**结论：保留旧 campaign，新增独立幽州地图标识、定义与存档槽；先精修一块可交互的方格样板，再扩充幽州内容。不能只把 `World.Width/Height` 改成 128，也不能把旧天下按比例放大。**

128×128＝16,384 格是工程提案，约为旧 36×27＝972 格的 16.86 倍；用户确认的是“先幽州、以后扩展、地图大很多”，没有指定精确格数。上一轮“弱化普通格线”的建议被新要求覆盖：正常操作视距下必须直接看清每一格，资源与归属均以方格为基础。程序低模原型运行通过不代表画质被接受。

## 2. 最小安全隔离方案

建议继续复用经济、武将、战斗和单支军队规则；新增地图定义与加载入口，不复制一整份 `World` 业务代码，也不把所有界面/渲染管线一起重写。

### 2.1 两种地图、明确上下文

| 项目 | 旧原型 | 新幽州工程样板 |
|---|---|---|
| 地图标识 | `legacy-campaign-v1`，仅为旧缺省档建立运行时身份 | `youzhou-preview-v1`（建议标识） |
| 尺寸 | 固定 36×27 | 提案 128×128 |
| 生成/布局 | 保留原布局，继续旧回归 | 独立 `YouzhouMapDefinition` 与内容生成入口；山脉、河流、道路、城池、出生点为幽州专用数据 |
| 存档 | 原 `campaign.json` / `.bak` / `.tmp` | 独立 `youzhou-preview-v1.json` 及自己的备份/临时文件 |
| 地区名称 | 旧13区映射 | 幽州本图的区域/据点映射；不复用旧天下编号语义 |
| 地图显示 | 旧渲染器保留为兼容路径 | 新方格/分块渲染器；资源采用精细原创 sprite 与少量模型混合 |

共享规则读取**当前 World 的地图上下文**，不再读取全局静态尺寸。建议引入 `MapWidth/MapHeight`、`TryGetLand(x,z)`、`GetRegionName(localRegionId)`、地图名称与出生锚点查询；旧 Width/Height 可以暂留为旧地图常量，逐项迁移活跃调用者，避免一次性破坏全部旧测试。

启动时先确定当前模式与存档槽，再创建地图，不能先在 Awake 生成天下预览后再切幽州。保留现有三文化旧开局作为旧入口；新样板入口明确写“幽州样板”，不要把 (17,13) 的旧天下相机背景当幽州。

建议新调试参数或显式内容配置选择地图；不要仅依赖场景名称，因为当前 RuntimeInitializeOnLoad Bootstrap 会自行生成 `EasternDynastyGame`。若以后单独构建预览，可使用独立输出目录；当前客户端可能仍在运行，不覆盖正在使用的 Build 或终止进程。

### 2.2 存档版本与加载顺序

建议新格式使用 saveVersion=2，包含 mapId、地图宽高、地图内容修订、生成器版本/种子；旧格式仍识别为 v1。此处是数据契约提案，尚未实现。

1. 用户选择的槽位决定允许加载的地图。只对 v1 且无新地图元数据的旧档，显式绑定旧36×27定义；不能让任何未知 mapId 自动退回旧图。
2. 新档要求 mapId 已知、尺寸符合该定义、修订可支持，才校验土地数量/坐标/ID/地区/主城/军队目标。不得通过从 lands.Count 猜图宽来恢复损坏档。
3. 校验后重建非持久化索引与缓存，再结算离线收入/行军，最后交给显示层。字段缺失的默认值要显式归一化，不依赖反序列化会执行构造器或字段初始值。
4. 复用目前临时文件写入、替换与备份策略，但槽位必须分别拥有 `.tmp/.bak`。继续游戏、自动保存、手动保存、退出保存全部使用**当前已建立 session 的槽位**，不能使用尚未确认的 UI 地图选择值。
5. 幽州槽位中若误放旧 campaign，或旧槽位中出现幽州 payload，应拒绝并解释，不静默转换。载入失败不能创建新世界后覆盖原文件。
6. 新预览/Smoke 应继承 TransientRun 的保护，确保测试退出不会写用户进度。旧客户端仍可能退出写 campaign.json，独立槽能避免相互覆盖。

首个128图可以继续保存完整 Land 列表，16,384 条普通数据对象不等于16,384个 Unity 场景物体。不要首轮就改为“仅保存种子+差量”并在加载时重生成土地；那会把生成器更新与已占领地、主城、行军目标绑定。确有体积需求后，再做有版本约束的确定性底图+差量方案。

### 2.3 Land ID 与后续区域扩展

首个幽州版本可保留局部 row-major ID：`localId=z*128+x`，以减少 `lands[id]` 规则的改动，但**该 mapId 的宽度必须固定**。旧图继续按36解码，绝不能用128重新解释原 homeId/order.target。

未来跨区域地址使用 `(mapId, localId)`，或 `(mapId, localX, localZ)`，再由对应地图解析。扩充其他州时增加地图定义与区域连接，不改变现有幽州宽度。若将来确实扩建幽州内部到更大尺寸，应作为显式新版本迁移，通过旧坐标转换全部引用并验证，不得只改宽度。

当前 `ArmyOrder.target` 只有局部整数，第一阶段只保证幽州内行军；跨图路线、连接口、目标地图与加载管理属于后续功能。可以预留地址类型，不能把“独立地图可扩展”误说成已完成跨州行军。

### 2.4 地区、文化与出生

将“幽州这张地图”“图内县域/分区”“汉地/草原/东北文化”分开。`Land.region` 可以暂作地图内局部分区索引，显示名称通过当前定义查询；`Homeland` 继续表达武将池与文化机制，不能由 region<9 之类条件推导。

首个幽州样板可以先提供一个明确的汉地出生锚点和若干同图备选位置；不需要为了保留旧三按钮，硬塞三种文化与13城进幽州。真实郡县名称、城池位置与地理须另行核对，未核对前使用明确的规划标识，不能把随机地形称为历史地图。

出生点按定义选择，并验证可通行、未占用、邻接资源和到目标城池的路径。不要固定“地区首都向西两格”，也不要无条件把周围山河抹成粮田。老地图的既有行为和检查保留在旧入口。

现有跨文化城池解锁卡池的规则依赖 `tile.homeland != world.origin`。若幽州样板尚无符合条件的异文化城池，就诚实显示该解锁路径本阶段未提供；不能为了演示解锁而把普通幽州城改成另一个文化。武将 definition ID、卡牌 uid、等级与阶数不因地区重命名而改变。

## 3. 方格、镜头与拾取

底层为等边 XZ 正方形网格，地块中心和边界统一从一个 GridTransform 计算：tileSize 固定，中心在 `(x*tileSize,z*tileSize)`，边界为中心±半格。斜视菱形外观由正交相机方位与俯角产生，不把数据坐标改成菱形，也不在屏幕上另画与世界不一致的网格。

- 常用近/中视距的格线必须稳定可见；细格线、整格归属覆盖、选中强边/角标为三个独立层。地形纹理可以连续，不能再次以“连续地貌”为由隐藏玩家需要的方格。
- 网格用共享地表 Shader 或每块合并的线网格，不创建每格 LineRenderer；格线宽度应随像素覆盖调整，避免斜视闪烁。
- 首轮固定镜头方位，允许平移与缩放。若用约45°方位角，当前拖动 `delta.x/delta.y*1.287` 的轴向公式不再正确，应通过前后鼠标射线与地表平面求交得到拖动量。
- 新图拾取优先射线与逻辑基准面求交，再将世界坐标转换到最近的格中心（等价于 floor(x/tileSize+0.5)），明确负坐标、边界及正好落在线上的规则，并检查0..127范围。
- 若确需起伏地形拾取，可仅为可见块生成块级地表碰撞网格，再由命中XZ计算格坐标；不建16,384个 LandHit/BoxCollider。
- 对外提供语义稳定的 `TryPickLand` 和 `SurfacePoint`；旧地图可以保留 LandHit 路径，幽州使用新实现。测试应核对目标 ID、HUD 遮挡和边界，而不是要求新图继续存在逐格碰撞体。
- 低分辨率、地图最远端和跨块拖动都要验证。不能通过限制玩家只能看出生点附近，掩盖其余幽州没有生成。

## 4. 可见块与精细2.5D资产

建议16×16逻辑格为一个渲染块，128图共8×8＝64块。这是起始调优值，不是性能保证。完整逻辑数据常驻；地表可以64块共享材质，资源、建筑与标签按可见范围加一圈预载创建/复用。只关闭 Renderer 能减少绘制，不能代替限制景物实例创建。

由相机视口射线在逻辑平面上的覆盖范围求候选块，再做裁剪并为高模型/大 sprite 留边距；不能假设任何分辨率/缩放下固定只需9块。块跨越、缩放或地图数据脏标记触发更新，不每帧销毁重建。设置创建预算与缓存上限，远离视口的景物可回收；选中与行军状态存在数据层，卸载图块不能丢失状态。

共享地表由较少网格顶点承载纹理与方格，不继续沿用旧 `WorldLandscape` 固定12块循环。16,384格的资源分类/归属元数据可做小型数据纹理或分块缓冲；128×128 RGBA8 仅64 KiB，不应为一个格色创建一个材质实例。

视觉资产推荐混合：精细原创农田/草场/石场/铁场 sprite，配少量具有真实体积的城墙门楼、桥梁与标志建筑。使用共同光向、底部锚点、格占地尺寸和阴影规则。先精修一组可在真实相机下辨识的资源资产，不能把旧低模渲染成图片就宣称完成画质升级。

单个 SpriteRenderer 仍是一个场景组件；不要用16,384个 SpriteRenderer 替换16,384个模型后称为分块优化。可见资源可按图集与层级合并四边形或按数量受控的池管理。透明排序、alpha边缘、城墙遮树与河岸遮挡必须做真实截图检查；透明物跨块排序可能出错，不能假设“一个大合批”自动正确。固定镜头有助于稳定烘焙视角和排序，旋转镜头属于另一个资产约束。

2.5D 不等于没有性能成本：大面积半透明、重叠阴影和多张大图集可能让 UHD630 更慢。2048² RGBA8 图集无 mip 为16 MiB，有完整 mip 链约21.3 MiB；正式平台压缩和实际纹理内存另测。地图与武将原画应分组管理，不让打开一张卡就常驻所有高清图。

近景显示资源细节、清晰格线和选择反馈；中景保留格与城市层级；远景降低资源细节，以地理、归属和城市标记承载信息。全图概览可以有单独的低成本表现；如增加导航小地图，优先使用逻辑数据生成低分辨率纹理，不再创建第二套逐格场景。

## 5. 查询与生成开销：必须一起改

| 当前热点 | 对128图的最小调整 |
|---|---|
| `AttackProblem` 全表 Any 查相邻己方土地 | 用当前格四个合法坐标直接查询，保持曼哈顿四邻规则，不增加对角邻接；注意边界不能通过 id±1 跨行 |
| Tick 每帧调用 HourlyIncome；收入又扫描已占格和城池 | 所有权、等级或加成变更后重算/增量维护收入；加载后重建缓存，时间推进只按已确定速率结算 |
| OwnedCount/OwnedCapitals 多处 LINQ 扫描，MapView每帧用数量判断刷新 | 由占领/加载/新局事件更新计数与脏块；不能只根据数量猜所有权没变，因为交换地块数量可能相同 |
| OnGUI 多次枚举全 lands 找城并排序 | 单独维护城市索引，先过滤可见范围，复用标签布局状态；GUIStyle与临时列表避免逐标签反复创建 |
| `WorldLandscape.Height` 全表水距，且生成法线多次调用Height | 幽州生成阶段缓存高度/岸线；河段按空间块索引，只查询附近河段。别把128图所有河段带进每个顶点采样 |
| RefreshOwnership 遍历全图并重建完整边界 | 先改为事件触发；进一步只重建变化块与相邻块的覆盖/边界 |
| 当前 BFS 在每个节点扫描全部土地 | 新测试与寻路使用四邻索引，做到O(V+E)；16,384节点的全表邻居方式最坏约2.68亿次候选检查 |

缓存须可重建，不能成为存档中的第二份真相。当前 Land 字段公开，测试和工具可能直接赋 owned；统一修改入口或在测试夹具变更后显式重建索引，避免缓存造成经济/解锁规则失真。

当前行军时长按主城到目标的欧氏距离计算，路径显示为直线，并非沿可走地形寻路。幽州扩大后这一差距更明显：本迁移阶段应保持并标注当前规则，不能把直线动画当成已实现道路/桥梁寻路。若本阶段要改寻路，应作为独立规则变更验收。

## 6. 测试与验收矩阵

保留旧146项核心检查及旧四状态序列化样本；新增幽州组，不把旧13城/15水格断言直接改成新图数量。下表是待实施检查，不是已通过结果。

| 类别 | 幽州必须验证 |
|---|---|
| 地图定义 | 128×128提案产生16,384格；每格坐标/ID唯一且相互可逆；区域索引均在本地图定义内；没有套用旧13城布局 |
| 边界邻接 | (0,0)、(127,127)、边缘格四邻正确；id127与128不因差1变成左右邻居；地图外查询安全失败 |

| 存档隔离 | 新局、保存、30秒自动存、退出、主档损坏回退备份都只操作当前slot；幽州测试运行前后旧campaign及bak哈希不变 |
| 序列化 | 两种地图均覆盖驻守、出征、返城、已返回；保留 homeId、orders目标、资源、卡uid、阵容、已占地；地图内容修订不同不得静默重生成 |
| 拾取 | 近/中/远缩放，三分辨率，四角、格中心、格线两侧、跨块边缘的屏幕坐标都回到同一逻辑格；HUD/卡牌/小地图阻挡不会误点地块 |

Editor 的 VerifySerialization 需按地图参数分别输出样本；当前文件名 `serialization-idle.json` 等不区分地图，应增加地图目录以保留旧证据。运行 Smoke 增加地图选择与独立截图目录，幽州使用 TryPickLand 验证，不要求逐格 LandHit。Validate-Visual 的固定12截图清单可以保留旧组，新组增加方格近中远、跨块、远端导航与地图边界，不能单纯放宽截图数量就算通过。

性能继续在同一 UHD630 与三分辨率记录，但必须说明测量方法。上一轮1920×1080的120帧样本 p95 为33.37ms，已经存在掉帧；新图不能继承“稳定60”结论。增加CPU/GPU分项、移动跨块时长、首次可交互时间、峰值内存及创建/回收计数；不限帧测试和限帧体验测试分开。场景物体预算和帧时目标应在精细局部实测后确定，而不是先承诺16,384格全画也流畅。

## 7. 建议执行顺序与本轮边界

1. **先定精细局部**：一个16×16或更小的幽州候选区域，含普通方格、四类资源、城池、河岸/通路；同时精修一张武将卡。提交实际客户端近中远截图，对照真实参考与用户要求。它是局部画质样板，不能称为整张幽州已完成。
2. **隔离数据与存档**：地图定义、地图上下文、独立slot、旧档兼容；原玩法继续复用。启动不再先生成旧天下。
3. **建立可见块与网格拾取**：替代逐格物体，完成边缘/遮挡/跨块检查；把经济和邻格扫描改成与扩大规模相称的查询。
4. **扩至128工程提案并填入幽州结构**：保持已验收资产规范和方格尺度，增加内容修订与地理核对；不要随机铺满同一批素材冒充完整地区。
5. **实测后扩充区域**：以后以新mapId与区域连接扩展，不重排既有幽州ID；正式跨州行军、多人和服务器仍是独立工程。
