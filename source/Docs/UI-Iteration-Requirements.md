# 每轮必须改进 UI

用户于 2026-10-26 再次反馈：“UI 我看了还是太老土，离率土之滨的 UI 差着远呢”，明确要求后台进程每次都更新 UI。本要求适用于之后每一轮开发，优先于旧 Backlog 中仅增加玩法功能的排期。

## 2026-10-27 方法更新：专业工具先行

用户要求停止凭想象写UI，先研究与调用专业设计工具并参考原作。执行 [专业UI流程](Professional-UI-Workflow.md)：原图测量 → 可编辑分层稿 → Inkscape实际导出与查看 → 按稿实现 → 原图/设计/运行截图对照。每轮UI记录必须引用源稿、导出收据与预览；没有设计依据不能继续加自制程序美术。Figma尚未连接，不得假称调用；测量模板、位图概念稿不等于成品或可运行UI。

## 每轮交付要求

1. 每轮至少完成一个玩家能直接看到的、实质性的界面改进。玩法、规则、资料同步和测试工作可以并行开展，但不能替代本轮 UI 工作。只加文字、按钮或页面，微调颜色、边距，改日期、写计划，均不算实质性视觉改进。
2. 先实际查看至少一张相关《率土之滨》原图，以及同页面最近可用的游戏截图，写出至少三个具体差距，再决定本轮方案。素材和布局依据来自 RAG 与本地素材集；原图年代、赛季或适用范围不确定须注明。没有当前源码截图时准确注明基线版本，不能把旧图当成本轮运行结果。
3. 优先改善玩家最常见的大界面：地图主 HUD 与导航、主城内部全景与设施界面、武将卡面与详情；随后改善任务、部队、练兵和战报。不要持续新增冷门子页面而让主界面原样保留。先改善其中一整块区域，保持其余入口可用。
4. 从构图与信息层级、图片和图标的使用、面板材质与透明度、字重与字号、间距与对齐、按钮状态与反馈中，选择能解决本轮具体差距的组合。配色与比例以选定参考图为依据，避免把通用网页卡片、整页文字或统一换色当作策略游戏美术。复用并逐步统一现有视觉样式，避免各页继续形成不同风格。
5. 同时照顾 Windows 与 Android 横屏的安全区、触控目标、滚动和返回；地图、卡面和城景不能被文字与常驻大面板淹没。保留存档、玩法、点击区域和既有验收，不通过隐藏内容或删除失败检查制造进步。

## 证据和交接

- 每轮写 `Docs/UIIterations/<context.version>.md`：目标页面；原作参考图路径及范围；游戏基线截图路径和版本；三个具体差距；本轮实际修改的布局/美术/资源及代码文件；预期截图状态；尚存差距。
- 开发阶段仅执行允许的纯逻辑/编译检查，更新截图和交互验收入口，由独立发布任务在固定快照中生成本轮实图。开发报告必须区分“UI 源码完成”和“运行观感已验收”，不能虚构修改后截图。
- 结构化结果的 `changes` 必须明确列出本轮可见 UI 变化，`evidence` 引用上述记录，`remaining` 写清视觉差距和待运行验收项。未完成 UI 必须明说，不能用测试数量或新增功能宣称满足本轮 UI 要求。
- 严重功能回归仍需先修复；同轮继续完成有界的 UI 改进。若时间不足，准确交接未完成项，不为凑次数破坏功能或伪造完成。

## 发布视觉审查

含本要求的候选必须检查本轮 UI 记录，并实际查看对应页面的新截图，与原作参考和基线对照。审查布局、视觉层级、图像占比、文字密度、风格一致性以及桌面/手机可读性；功能检查通过不能替代视觉审查。

没有实质 UI 变化、缺少目标页面的新运行截图，或改后仍有明显重叠、裁切、不可读、主要入口不可达时，应返回 `blocked` 并给出可执行的修正项。指出改善了哪一处及仍有何差距，不能无依据宣称已经接近或还原原作。旧候选没有本要求时不伪造补填新的开发记录。
